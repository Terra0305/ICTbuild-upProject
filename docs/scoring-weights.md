# 매칭 점수 가중치 근거와 민감도

기획서 §8.3은 가중치를 "초기값, 검증 데이터로 조정"이라고만 적었다. 이 문서는 초기값을 왜 그렇게 잡았는지, 흔들면 결과가 얼마나 바뀌는지, 실데이터가 생기면 무엇을 다시 확인할지를 남긴다.

## 1. 현재 가중치

`final_score = Σ(사용 가능한 항목 점수 × 가중치) / Σ(사용 가능한 가중치)` — 정보가 없는 항목은 0점이 아니라 분모에서 뺀다.

| 항목 | 가중치 | 왜 이 크기인가 |
|---|---:|---|
| 텍스트(설명 임베딩) | 0.35 | 물건을 구분하는 정보가 가장 많이 담긴다. "검은 카드지갑"과 "갈색 장지갑"처럼 종류가 같아도 특징으로 갈린다. |
| 이미지 | 0.25 | 사진이 있을 때 가장 직관적인 단서. 다만 습득물 사진이 없는 경우가 많아 없으면 자동으로 빠진다. |
| 카테고리 | 0.15 | 후보 조회 단계에서 이미 같은 종류만 남기므로(`_is_plausible`) 점수 차이를 만드는 힘은 작다. |
| 색상 | 0.10 | 같은 종류 안에서 걸러 주는 보조 단서. 표기가 제각각이라 오인식 위험이 있어 크게 주지 않았다. |
| 지역/거리 | 0.10 | 지역 불일치는 후보에서 제외(하드 필터)하므로, 점수에서는 가까움의 정도만 반영한다. |
| 날짜 | 0.05 | 분실 후 습득까지 걸린 시간은 약한 단서. 180일 창 안에서는 큰 차이를 만들지 않는다. |

하드 필터(카테고리 불일치, 날짜 창, 다른 시·도, 5km 초과)는 점수가 아니라 후보 자격이다. 점수 가중치와 별개로 동작한다.

## 2. 민감도 분석

`docs/eval/run_weight_sensitivity.py`로 가중치를 하나씩 ×0.5, ×1.5 로 바꾸거나 제외했을 때 정답이 몇 위에 오는지 비교했다. 같은 검증셋(질의 60건 × 시드 5, 습득물 660건)과 평가 방식은 `docs/eval/run_eval.py` 와 같다. 결과 원본은 `docs/eval/weight_sensitivity.json`.

- **normal**: 정답 습득물이 분실 후 0~9일, 같은 동네 경찰서에 있는 쉬운 설정
- **strict**: 분실 후 0~60일, 5km 안 임의 경찰서 — 날짜·장소가 정답을 가려 주지 못하는 어려운 설정

### strict 결과 (MRR, 높을수록 좋음)

| 시나리오 | R@1 | R@5 | MRR |
|---|---:|---:|---:|
| **기준 0.35/0.15/0.10/0.10/0.05** | 78.3 | 97.7 | **87.0** |
| 텍스트 ×0.5 | 68.3 | 95.0 | 80.3 |
| 텍스트 ×1.5 | 79.7 | 99.3 | 88.1 |
| 색상 ×0.5 | 74.3 | 97.3 | 84.3 |
| 색상 ×1.5 | 79.3 | 97.7 | 87.7 |
| 지역 ×1.5 | 73.7 | 96.7 | 84.2 |
| 날짜 ×1.5 | 74.3 | 97.0 | 84.5 |
| 텍스트 제외 | 31.3 | 87.3 | 54.6 |
| 색상 제외 | 53.0 | 85.3 | 66.4 |
| 텍스트만 | 72.0 | 92.3 | 81.0 |
| 균등 가중 | 42.7 | 91.7 | 63.8 |

normal 설정 결과는 `weight_sensitivity.json`에 있다. 기준 MRR 96.7 이고 단일 가중치를 ±50% 바꿔도 95.9~96.9 에 머문다.

### 읽는 법

1. **텍스트와 색상이 가장 민감하다.** 빼면 strict MRR이 87.0 → 54.6 / 66.4 로 크게 떨어진다. 이 두 항목은 정확도가 곧 서비스 품질이다. 그래서 색상 인식 개선(`app/ai/colors.py`)이 점수 개선에 직결된다.
2. **단일 가중치를 ±50% 흔드는 정도로는 결과가 거의 안 변한다.** normal 에서는 ±1점 안, strict 에서도 대부분 ±3점 안이다. 단, 텍스트 ×0.5 는 -6.7점이라 텍스트를 줄이는 방향은 위험하다.
3. **텍스트 ×1.5 가 strict 에서 +1.1점 낫지만 normal 에서는 -0.8점이다.** 차이가 질의 60건 규모의 노이즈 안이라 현재 값을 바꿀 근거로 보지 않는다.
4. **균등 가중은 명확히 나쁘다**(strict MRR 63.8). 항목마다 신뢰도가 다르다는 가정이 맞다.
5. **지역·날짜를 키우면 strict 에서 손해**(-2.8, -2.5). 약한 단서에 큰 가중을 주면 오히려 정답을 밀어낸다.
6. 카테고리는 이 검증셋에서 판단 불가다. 후보 조회에서 이미 같은 종류만 남기므로 모든 후보의 카테고리 점수가 같다. 가중치를 바꿔도 순위에 거의 영향이 없다.

## 3. 이 분석이 말해 주지 않는 것

- **합성 검증셋이다.** 질의 60건은 팀이 만든 분실물/습득물 쌍이고, 실제 LOST112 습득물 문구의 분포와 다르다. 절대 수치(R@1 78~94%)는 서비스 정확도로 인용하면 안 된다. 가중치끼리의 상대 비교로만 쓴다.
- **이미지는 평가에 없다.** 검증셋에 사진이 없어 0.25 가중치는 검증되지 않았다.
- **색상 표기 가정이 반영돼 있지 않다.** 검증셋은 우리가 정한 색상 코드를 직접 쓴다. 실제 LOST112가 "검은색/빨간색/하얀색"으로 내려주면 인식률이 달라진다. 이 부분은 `scripts/audit_found_colors.py` 로 실제 표기를 확인해야 한다.
- 로컬에 ONNX 모델 파일이 없어 같은 모델의 fp32 캐시로 임베딩했다. 배포 모델은 int8 양자화본이라 텍스트 점수가 소폭 다를 수 있다. 가중치 간 상대 비교에는 영향이 작다고 보지만 수치가 정확히 같다고 보장하지는 않는다.

## 4. 실데이터가 생기면 다시 할 일

1. **정답 라벨을 모은다.** 사용자가 분실물을 `MATCHED_BY_REFIND` 사유로 종료한 건의 매칭이 "맞은 후보"다. 반대로 상위 5위에 오르고도 끝내 선택되지 않은 후보는 약한 음성이다.
2. 라벨이 30건 이상 쌓이면 `run_weight_sensitivity.py` 의 검증셋을 실데이터로 바꿔 같은 표를 다시 만든다.
3. 색상: `scripts/audit_found_colors.py` 결과에서 미인식 표기가 많으면 `app/ai/colors.py` 에 추가한다.
4. 사진 가중치(0.25)는 사진이 있는 라벨이 충분해진 뒤에 별도로 검증한다.
5. 바꿀 때는 하나씩, 이 문서의 표를 갱신하면서 바꾼다.

## 5. 점수를 읽는 사람에게 보여 주는 방법

가중치가 무엇이든, 비교에 쓰인 항목이 적으면 점수의 의미가 약해진다(분모에서 빠진 항목이 많기 때문). 후보 카드에 "6개 중 N개 항목 비교됨"을 표시하고 3개 이하이면 참고용임을 안내한다. 점수를 확정 확률처럼 읽지 않게 하기 위해서다.
